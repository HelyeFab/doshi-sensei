In fact, you're utilizing Netlify’s Functions (AWS Lambda under the hood) for your Next.js API routes, and even offloading some functions to Firebase Cloud Functions. This means any Next.js API route or dynamic page is executed in a serverless context (no always-on Node server). The site’s primary domain (doshisensei.com) is hosted on Netlify (as evidenced by the errors coming from that domain), and certain background tasks or services have been moved to Firebase. In summary, the deployment is a static front-end on Netlify, augmented by serverless API endpoints on Netlify and Firebase.

Middleware and API Routes Potentially Causing Delays
You have identified several parts of your app that could be contributing to the slow responses or timeouts:
Next.js Middleware (/src/middleware.ts): This runs on every request (as an Edge Function on Netlify). It handles things like RSC requests, security headers, and routing logic. Generally, your middleware should be lightweight, but any added delay here affects all requests. (Netlify Edge Functions have very short time limits ~50ms by default
netlify.com
, but presumably your middleware is simple enough not to exceed that.)
Heavy API Routes: A number of Next.js API endpoints perform intensive operations:
/api/admin/* – Administrative operations that might fetch a lot of data or perform complex queries.
/api/ai/explain – Calls out to the OpenAI API. These calls can be slow (depending on the prompt and OpenAI response time) and also need proper error handling.
/api/youtube/extract – Likely calls a Supabase (SupaData) service to get YouTube transcripts. This might involve a third-party HTTP request which could sometimes be slow.
/api/tts/* – Text-to-speech generation, possibly calling an external TTS service or heavy library.
/api/textbook-vocabulary/* – Possibly fetching or processing a large list of vocabulary from a database.
/api/stripe-webhook and other payment-related routes – Handling Stripe events (though these are invoked by Stripe, not the user directly). If these crash or are slow, it might not directly cause a user-facing 502 on navigation, but any unhandled error here is worth noting.
Each of these routes runs as a serverless function on Netlify. If any single one of these API calls or data-fetching operations is slow (for example, waiting on a slow external API or processing a large amount of data), it can delay the server’s response to the user. In the context of Next.js 13 App Router, your pages might be using Server Components or getServerSideProps that call these APIs on the fly. A “drill” or “vocabulary” page, for instance, might be calling the textbook-vocabulary API or querying a database for a large dataset at request time. If that operation takes too long, the user’s navigation will hang and eventually error out. Potential culprits for timeouts include: large data fetches (like loading an extensive vocabulary list), multiple sequential external API calls (OpenAI, YouTube API, etc.), or complex server-side computations. If, for example, the drill page is aggregating a lot of stats or the admin page is pulling a ton of records, those could easily exceed the time budget.

Root Causes of the 502 Errors
Taking all the above into account, the likely causes for the 502 errors are:
Serverless Function Timeouts: The most straightforward cause of a 502 in this context is that the Netlify function did not return a response in time. Netlify’s default execution limit for synchronous functions is around 10 seconds
meje.dev
 (by design, Lambdas are short-lived). Even on Vercel, which is the reference host for Next.js, the serverless functions max out at ~10 seconds by default
stackoverflow.com
. On Netlify, Pro tier users can request an increase up to ~26 seconds max
answers.netlify.com
answers.netlify.com
, but anything beyond that isn’t possible without rewriting the architecture. Your logs indeed show functions hitting ~10 seconds and then being terminated. In one forum example, Netlify staff noted that certain requests “take longer than 30 seconds to start sending a response,” and those get cut off with a 502 status at the 30s mark (Netlify’s front-end gateway will abort if nothing is sent by then)
answers.netlify.com
. In your case, it seems the cutoff was ~10 seconds (likely because that’s the set limit for your site’s plan). Simply put, any page or API route taking >10 seconds to execute will result in a 502 Bad Gateway (Netlify’s gateway reports that it got no valid response from the function in time).
Heavy Server-Side Processing and Data Fetching: Underlying those timeouts is the fact that some pages are doing a lot of work on the server side. Next.js server-side rendering can be slow if misused – for example, if you fetch large amounts of data or call external services serially during the request. In a discussion of Next.js performance, developers noted that heavy SSR tasks (like waiting on slow APIs or large data processing) will delay the page rendering
reddit.com
. In your app, the vocabulary, drill, and admin pages likely trigger large database queries or multiple API calls. If each of those calls takes a few seconds, or if there are hundreds of database records to serialize, the total time easily adds up past the limit. The fact that multiple routes are failing suggests that many parts of the app have this issue. It’s essentially overloading the serverless function with too much work at once (for example, generating a big JSON payload for a vocab list, summarizing data for drills, contacting OpenAI and waiting for a response, etc.). Each of these operations is prone to latency:
External APIs (OpenAI, YouTube, Stripe) might take several seconds or more, especially if rate-limited or dealing with large content (like a video transcript).
Database or Supabase calls could be slow if the dataset is large or not indexed properly.
Generating large HTML or JSON (React Server Component payload) for the page means more computation and more data to send, which takes time.
In short, heavy data fetching and processing on the server-side is a major factor. One article on Next.js performance specifically calls out “heavy data fetching” as a common cause of slow apps
blog.logrocket.com
. Your app seems to hit this: by trying to do everything on-the-fly per request, it runs into performance bottlenecks.
High Memory and CPU Usage: The serverless function logs showing ~300+ MB memory usage are a symptom of how much data is being handled. While 300 MB is within the 1 GB limit, it suggests that the function might be pulling in a lot of data into memory (e.g., a large array of records, or big objects like transcripts). High memory usage often correlates with heavy CPU usage as well (for example, parsing a large JSON or performing computations on a large array). In AWS Lambda (which Netlify uses), CPU power is proportional to the memory allocated – with 1024 MB you get a certain CPU share. If you are maxing out CPU doing data processing, even 10 seconds may not be enough to finish. Also, if memory were ever to spike above the limit, the function would crash (though your 339 MB is not above the limit, so the crashes are likely due to timeouts or code errors, not out-of-memory). Still, handling very large payloads in a single request can slow things to a crawl.
Unhandled Exceptions in Server-Side Code: Another cause of 502s can be outright errors in the code. The logs showed an UnhandledPromiseRejection for a Stripe-related operation. This means a promise (likely an async call to Stripe’s API or SDK) failed and there was no .catch to handle it. In Next.js serverless functions, if an exception is thrown (or an unhandled promise rejection occurs), the function will crash and the user sees a 502 (since the proxy sees it as an invalid response). This is actually a known behavior: “any exceptions thrown while server-side generating… will cause a 502”
github.com
 (instead of a nicely handled 500 error page, in many cases). So, some of your 502s, especially those that happened quicker (e.g., a request failing at ~4 seconds as seen in the screenshot, instead of at 10 seconds) could be due to a code error. For instance, the Stripe script failing to load might throw immediately, or an API call might reject if given a bad input, and if that isn’t caught, the function exits early with a 502.
Multiple Concurrent Requests (Prefetch Overload): This is related to point 2, but worth noting: if the homepage triggers prefetch for, say, three heavy pages (vocabulary, drills, practice) simultaneously, you now have three serverless functions running at once, each doing heavy work. This can strain your available memory/CPU even further and possibly contend with each other. Netlify functions scale with concurrent requests, but if they all hit a shared resource like a database, that could become a bottleneck. In any case, concurrent heavy functions could saturate the server CPU such that none of them finish quickly. The log snippet showing multiple pages all failing around the same time suggests this might be happening. It’s essentially a thundering herd problem: the app tries to be too “helpful” by pre-loading lots of content, but ends up DDoSing itself.
In summary, the 502 errors are the result of serverless functions not completing successfully – either timing out due to too much work or crashing due to errors. The root causes are the limitations of the hosting platform (execution time limits, memory limits) combined with the app’s behavior (heavy data operations and some uncaught errors).
Recommendations and Solutions
Addressing these issues will likely require a combination of optimizing your code and adjusting your deployment strategy. Here are several steps and best practices to consider:
Optimize Server-Side Data Fetching: Review what data is being fetched or computed for those problematic pages. Can any of it be made static or cached? For example, if vocabulary lists or drills change infrequently, you could generate those at build time (Static Site Generation) or use Incremental Static Regeneration (Next.js ISR) to periodically update them. By doing so, you serve pre-built pages (or partial data) instantly from the CDN, instead of crunching everything on each request. Even using Next.js’s getStaticProps with a large dataset at build time is better than at runtime, as it won't hit the 10-second limit (build can take longer and is a one-time cost). If build-time generation is too slow or large, consider on-demand ISR where you trigger updates via a webhook when data changes. The goal is to shift heavy work out of the request lifecycle.
Break Up Long Tasks: If certain pages genuinely need to do a lot of processing, try to split the work. For instance, if a page currently fetches 5 different APIs sequentially, try to do them in parallel with Promise.all (so they all race together, making use of the full 10 seconds more efficiently)
blog.logrocket.com
. If one API call is very slow, consider loading that content lazily on the client side after initial page load (show a spinner or "Loading extra data..." message rather than blocking the whole page). For large dataset processing, consider pagination or infinite scroll so you only load a portion at a time. Essentially, don’t load or compute 1000 items if the user only needs to see 10 at a time.
Use Background Functions or External Jobs: Netlify offers background functions (15-minute limit) for tasks that don’t need to return immediately. For example, generating a YouTube transcript could be a background job: the front-end triggers it and immediately returns a response like “Transcript is being prepared”, then the background function can store the result in a database or file. Next time, the page can quickly load the cached transcript. Since you already use Firebase Functions, you could offload heavy tasks there as well – Firebase Functions (especially the paid plan or second gen) can allow longer execution times (up to 60s or more) and more memory. The idea is to move heavy lifting off the critical path of the user’s HTTP request. Use queues or scheduled jobs if needed for things like AI explanations or text-to-speech generation, so that when a user requests it, perhaps it's precomputed or can be fetched quickly from storage.
Implement Graceful Error Handling: Go through those API routes and wrap external calls in try/catch. For example, ensure your OpenAI call has a timeout or catch, and if it fails, respond with an error message (maybe a 504 or a custom error JSON) rather than letting an exception bubble up. For Stripe, make sure any initialization (like loading Stripe SDK or hitting their API) is in a try/catch as well. This way, if Stripe is down or slow, your function can still respond (perhaps with res.status(500).send("Stripe error")) instead of crashing. Catching errors and returning a controlled response will avoid the 502 scenario (Next.js could then render your error state or at least not hang). Remember, an exception = 502
github.com
 in many Next.js serverless setups, so preventing exceptions is key. Log the errors to your console or an error tracking service for debugging, but ensure the function itself responds one way or another.
Reduce Payload Sizes: If your pages are sending huge JSON payloads to the client (for example, maybe the RSC payload for a vocabulary page is enormous), try to trim it. Send only the data needed for initial render, or implement pagination. Large responses not only take longer to generate but also longer to transfer. Netlify has a response payload limit (around 6 MB for buffered, 20 MB for streamed responses)
docs.netlify.com
docs.netlify.com
 – large payloads risk hitting those limits or simply slowing things down. Check if images or other assets are being dynamically processed (like Next/Image optimization) – as an example, Next/Image on Netlify was causing 502s because the image processing function timed out after 10s when images were large
meje.dev
. The solution there was to disable that optimization or make it faster. Similarly, if any data processing is very heavy, consider doing it incrementally or with more efficient algorithms/libraries.
Manage Prefetching Behavior: As noted, Next.js prefetching can overwhelm your serverless functions. You can selectively disable prefetch on links that lead to very heavy pages. Using <Link href="..." prefetch={false}> will ensure Next doesn't automatically fetch that page’s data until the user explicitly clicks. Yes, it may make actual navigation a bit slower for that page, but it’s better than hammering your server with multiple heavy requests in parallel. You could also consider using Next’s built-in Suspense and lazy data fetching for parts of the page, so that not everything loads at once. For instance, maybe load basic page framework first, then stream in the large list or heavy component after a delay. This can make the initial response lighter and faster (and avoid hitting the timeout for the first chunk). In React 18, you can utilize streaming and <Suspense> boundaries such that some content loads after the main content is sent.
Leverage Response Streaming: Netlify supports streaming responses for synchronous functions
docs.netlify.com
. This means your function can begin sending some HTML to the client while still processing the rest. If you can refactor your page rendering to output partial content early (even just a header or loading message), it might reset the timeout counter since data has started flowing. This is advanced and depends on Next.js’s support for streaming SSR (which React Server Components are actually built to leverage). Ensure you're using Next 13’s streaming properly – if you flush some part of the response in under 10 seconds, Netlify might allow the function to continue up to the 30s total as long as it’s sending data. (According to Netlify docs, 30 seconds is the overall limit, but the initial response must start sooner
answers.netlify.com
.) So, utilizing streaming can keep the connection alive. However, this may require low-level tweaks; by default Next.js should be streaming the RSC payload as it generates it. If it’s not, perhaps the work is all happening before anything is sent. Introducing some early flush() or splitting the work could help.
Increase Function Timeouts (Last Resort): If after optimizations you still absolutely need more time, on Netlify you can request a timeout increase. On Pro plans, support can raise the limit to 26 seconds max for your functions
answers.netlify.com
. This could Band-Aid the issue for moderately slow functions. Keep in mind 26s is the upper ceiling; you cannot go beyond that on Netlify’s platform. And a 26-second server response is not great for user experience anyway (users might have given up by then). Still, it can prevent errors if some operations are just occasionally slow. You’d have to contact Netlify support (as you might know, they've done it for others on Pro
answers.netlify.com
answers.netlify.com
).
Consider Alternative Architectures: If these pages remain very data-heavy, you might consider moving them to a dedicated server or a platform like Vercel, which is optimized for Next.js. Vercel also has a 10-second limit for serverless functions by default, but they support Edge Functions and other optimizations for Next 13. Interestingly, one developer found that a Next.js image-heavy page that timed out on Netlify ran fine on Vercel
meje.dev
. This suggests Vercel’s infrastructure (or default timeouts) might handle certain Next.js features more gracefully (possibly by offloading image optimization to their own service, etc.). If you stick with Netlify, another approach is deploying a custom Node server (instead of serverless) for the backend. For example, running your app on a DigitalOcean or AWS EC2 server would remove the 10s limit – but you’d lose the easy scaling of serverless. A middle ground could be to host only the heavy API on another service; e.g., your front-end stays on Netlify, but API calls go to a long-running server or to Firebase Functions with higher timeout. Since you already use Firebase, you might expand on that: e.g., have Next.js call a Firebase Function for the vocab data, which can run up to 60s and return the data (though the user will still wait, at least it won’t 502; you’d need a loading UI).
Monitor and Profile: Finally, add monitoring to pinpoint which part of the process is slowest. Use logging generously around external API calls (log timestamps before and after an OpenAI call, for instance) to see how long each step takes. Netlify’s function logs (and maybe enabling Netlify’s function traces or metrics) can help identify if it's CPU-bound or I/O-bound. If you find, for example, that 90% of the time is spent waiting for OpenAI, then the solution might be caching those results or requesting smaller responses from the AI. If the database query is slow, consider indexing or query optimization. If JSON serialization is slow (for huge arrays), consider streaming the response or using a more efficient serialization method.
Implementing the above should greatly reduce the frequency of 502 errors. In essence, make the serverless work lean and mean: do less per request, cache more, handle errors, and be mindful of the platform limits. By doing so, your Next.js app can stay within Netlify’s execution budgets and provide a smoother experience to users without those bad gateway errors.
